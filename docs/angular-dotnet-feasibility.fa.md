# امکان‌سنجی Angular و ASP.NET Core برای چاپ احسان

تاریخ: ۲۰۲۶/۱۱/۱۵ — مرحله: بررسی طرح و امکان اجرا، پیش از نقشه راه و توافق تجاری.

به‌روزرسانی همراه نسخه ۰٫۲ طرح: [تفکیک کار انجام‌شده، نفرساعت آتی، دستمزد و زیرساخت](project-budget.fa.md). بازه‌های اولیه این سند برای نسخه عملیاتی بنر هستند؛ زمان انسانی گذشته ثبت دقیق نشده است.

## نتیجه پیشنهادی

Angular و ASP.NET Core برای این پروژه کاملاً مناسب‌اند. آشنایی موجود در پروژه‌های دیگر، در صورت تجربه عملی و امکان استفاده از زیرساخت مستقل و مجاز، می‌تواند کفه تصمیم را از ووکامرس به توسعه اختصاصی تغییر دهد. صرف استفاده از این فناوری در سپیدز، به معنای آماده‌بودن فروشگاه یا مجازبودن انتقال کد آن نیست.

در این مرحله از Angular و .NET به‌عنوان گزینه ترجیحی برای ادامه امکان‌سنجی استفاده می‌کنیم؛ ابتدا طرح را با احسان تثبیت می‌کنیم. پیاده‌سازی زیرساخت واقعی و فرمول قیمت به بعد از تأیید طرح موکول است. نمونه موجود مستقل از فریم‌ورک است تا تغییر طراحی ارزان بماند.

## معماری متناسب با اندازه پروژه

- یک برنامه Angular برای صفحات مشتری و بخش مدیریت؛ بخش مدیریت و صفحه‌های کم‌کاربرد به‌صورت lazy-load.
- یک ASP.NET Core API با مرزبندی روشن کاتالوگ، قیمت‌گذاری، سفارش، فایل و پرداخت؛ در یک سرویس قابل استقرار.
- EF Core و یک دیتابیس رابطه‌ای. PostgreSQL انتخاب اولیه برای استقرار مستقل است؛ SQL Server در صورت ابزار، تجربه یا زیرساخت مناسب نیز قابل انتخاب است. انتخاب نهایی به بررسی هزینه و عملیات بستگی دارد.
- ذخیره فایل خصوصی خارج از ریشه وب، یا فضای شیءگرا سازگار با S3، با نگهداری اصل فایل و پیش‌نمایش جدا.
- یک دامنه و مسیر `/api` برای بک‌اند؛ احراز هویت مبتنی بر کوکی امن HttpOnly و محافظت CSRF برای درخواست‌های تغییردهنده در سناریوی وب هم‌دامنه. احراز هویت اپ موبایل در صورت نیاز آینده جدا طراحی می‌شود.
- هویت مدیران با ابزار استاندارد ASP.NET Core، دسترسی نقش‌محور و احراز هویت دومرحله‌ای. دریافت کد پیامکی مشتری یک یکپارچه‌سازی مستقل است و آماده فرض نمی‌شود.
- یک پردازش پس‌زمینه ساده برای کارهای لازم مانند بررسی وضعیت پرداخت و پردازش محدود فایل؛ صف توزیع‌شده و Redis فقط با نیاز واقعی.
- برای شروع به Kubernetes، میکروسرویس، API Gateway یا معماری چندسروری نیاز نداریم.

## بار فنی واقعی

وجود شش کارت روی صفحه اصلی ساده است. کار اصلی سفارش بنر شامل این موارد می‌شود:

1. فرم قابل استفاده در گوشی، اعداد فارسی، خطاهای قابل فهم و حفظ پیش‌نویس غیرحساس.
2. تعریف قواعد قیمت در سرور، آزمون مثال‌های واقعی و نگهداری نسخه تعرفه در سفارش.
3. دریافت فایل بزرگ، محدودیت دسترسی و اندازه، نگهداری خصوصی و حفظ فایل اصلی.
4. ایجاد سفارش، تلاش‌های متعدد پرداخت، تأیید مبلغ، رسیدگی به callback تکراری و تراکنش نامشخص.
5. پنل مدیریت سفارش، دانلود مجاز فایل، وضعیت تولید و ویرایش تعرفه.
6. استقرار، مدیریت اسرار، گزارش خطا، بکاپ و آزمون بازیابی.

امنیت محصول با انتخاب استک خودکار تأمین نمی‌شود؛ محاسبه سمت سرور، دسترسی فایل، هویت و پرداخت باید آزموده شوند. تست پیش‌طرح جایگزین تست این بخش‌ها نیست.

## سرعت بارگذاری و سئو

برای خانه و صفحه‌های معرفی محصول، پیش‌رندر استاتیک Angular انتخاب اولیه است؛ سفارش و پنل مدیریت در مرورگر اجرا می‌شوند. با این روش برای نسخه اول الزاماً سرور Node.js جدا برای SSR دائمی لازم نیست. تغییر محتوای پیش‌رندرشده باید فرآیند بازسازی/انتشار داشته باشد. قیمت واقعی همیشه از API دریافت و تأیید می‌شود. اگر به‌روزرسانی لحظه‌ای محتوای عمومی بدون ساخت مجدد ضروری باشد، راهبرد SSR یا رندر آن بخش را دوباره بررسی می‌کنیم.

PWA می‌تواند بعداً برای نصب و پوسته آفلاین اضافه شود؛ قیمت نهایی، فایل، اطلاعات شخصی و پرداخت وارد کش آفلاین عمومی نمی‌شوند. نصب‌پذیری و آفلاین‌بودن دو نیاز متفاوت‌اند. در مستندات فعلی Angular، Service Worker داخلی ابزار کش با امکانات محدود معرفی شده است؛ قابلیت آفلاین پیشرفته را آماده فرض نمی‌کنیم.

## میزبانی اولیه

ASP.NET Core روی Linux قابل میزبانی است؛ IIS یا سرور ویندوزی الزام این استک نیست. برای ارزیابی اولیه، یک سرویس مدیریت‌شده مناسب یا VPS حدود ۲ هسته و ۴ گیگابایت RAM، با فایل‌های بزرگ در فضای خصوصی جدا، نقطه شروع قابل آزمایش است؛ ظرفیت تضمین‌شده نیست و باید با حجم فایل و پردازش واقعی سنجیده شود.

پردازش PDF/TIFF ممکن است منابع بیشتری بخواهد. محدودیت حافظه، زمان پردازش و اندازه فایل لازم است. هزینه نهایی شامل دامنه، سرور، فایل، ترافیک، بکاپ، پیامک، پایش و زمان نگهداری است. صرف انتخاب .NET هزینه لایسنس ویندوز یا SQL Server ایجاد نمی‌کند.

برای پروژه جدید .NET 10 LTS گزینه اولیه است، مطابق سیاست پشتیبانی بررسی‌شده در این تاریخ. نسخه دقیق Angular و بسته‌ها بعد از بررسی سازگاری و چرخه پشتیبانی در شروع پیاده‌سازی تثبیت می‌شود؛ نسخه‌های قدیمی پروژه دیگر را خودکار منتقل نمی‌کنیم.

## برآورد تلاش برای نسخه عملیاتی اول

این تخمین کارشناسی اولیه است، نه نرخ بازار یا تعهد تحویل. فرض‌ها: توسعه‌دهنده مسلط، یک زبان، یک درگاه، یک مسیر بنر، تعرفه‌های مشخص، مدیریت ساده، یک روش تحویل پایه، پنج دسته معرفی/تماس، بدون طراحی آنلاین و حسابداری. قابلیت آپلود بسیار حجیم با ادامه خودکار چندبخشی در برآورد پایه نیست.

| بخش | شروع مستقل از صفر، نفرساعت |
|---|---:|
| تثبیت طرح و قرارداد داده‌های اولیه | ۱۲–۲۰ |
| پایه پروژه، هویت و ساختار مشترک | ۲۴–۳۶ |
| رابط مشتری و مسیر سفارش بنر | ۳۶–۵۲ |
| API سفارش و قیمت‌گذاری توافق‌شده | ۲۸–۴۴ |
| دریافت و حفاظت فایل | ۲۰–۳۲ |
| پرداخت و بازیابی حالت‌های نامشخص | ۲۰–۳۲ |
| مدیریت سفارش و تعرفه | ۲۴–۴۰ |
| آزمون، استقرار، بکاپ و تحویل | ۳۶–۵۲ |
| **مجموع پایه** | **۲۰۰–۳۰۸** |

برای برنامه‌ریزی گرد شده: ۲۰۰–۳۱۰ نفرساعت پایه. با ۲۰ تا ۳۰ درصد ذخیره عدم قطعیت: حدود ۲۴۰–۴۰۰ نفرساعت. با ۳۰ ساعت کار متمرکز در هفته: حدود ۸–۱۳ هفته؛ این تبدیل ظرفیت است و انتظار برای درگاه و بازخورد مشتری جداست.

اگر پایه مستقل، سالم، قابل نگهداری و مجاز برای هویت، پنل و استقرار موجود باشد، تخمین پایه ممکن است به ۱۴۰–۲۲۰ ساعت برسد؛ با همان ذخیره حدود ۱۷۰–۲۹۰ ساعت و حدود ۶–۱۰ هفته با ظرفیت فرض‌شده. پیش از بررسی پایه موجود، این صرفه‌جویی قطعی نیست.

برای خود طراحی اولیه و نمونه قابل کلیک، بودجه زمانی حدود نیم تا دو روز متمرکز بسته به تعداد رفت‌وبرگشت مناسب است؛ این زمان با آماده‌سازی محصول عملیاتی یکی نیست. تجربه کمتر و یادگیری، زمان تقویمی را بیشتر می‌کند؛ تولید کد با AI زمان آزمون و عملیات را حذف نمی‌کند.

## مدل برآورد دستمزد

هزینه توسعه = نفرساعت توافق‌شده × نرخ ساعتی توافق‌شده. قیمت ریالی بازار در این بررسی استعلام نشده است.

برای درک مقیاس، اگر صرفاً یک نرخ فرضی ۵۰۰ هزار تومان در ساعت انتخاب شود، بازه ۲۴۰–۴۰۰ ساعت به ۱۲۰–۲۰۰ میلیون تومان می‌رسد. این مثال پیشنهاد قیمت بازار یا مبلغی برای اعلام به احسان نیست. با نرخ دیگر، عدد متناسب عوض می‌شود؛ استفاده مجاز از پایه آماده نیز تلاش را تغییر می‌دهد.

دامنه، زیرساخت، خدمات بیرونی و پشتیبانی بعد از تحویل جدا محاسبه می‌شوند. اگر بودجه کمتر از این مقیاس باشد، باید محدوده نسخه عملیاتی را کوچک‌تر کنیم، زیرساخت آماده مجاز داشته باشیم، یا ووکامرس را دوباره مقایسه کنیم؛ پایین‌آوردن ساعت آزمون پرداخت و فایل راه مناسبی برای کاهش هزینه نیست.

## تصمیم‌های همین مرحله

اکنون فقط این موارد را با احسان مرور می‌کنیم: چینش صفحه اصلی، نام دسته‌ها، مسیر مرحله‌ای بنر، نقش تماس برای پنج دسته دیگر، و نمای ساده پیگیری/مدیریت. سؤال‌های تعرفه و عملیات در فهرست باقی می‌مانند و هم‌زمان وارد همه آن‌ها نمی‌شویم.

پس از تأیید طرح، گام بعدی بررسی پایه فنی موجود و قرارداد قیمت‌گذاری با مثال واقعی است؛ سپس نقشه راه و برآورد اصلاح‌شده تهیه می‌شود.
